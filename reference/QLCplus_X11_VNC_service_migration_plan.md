# Raspberry Pi 5 — Migration Openbox Autostart → systemd services for X11/VNC/QLC+

## Purpose of this document

This document is the hand-off specification for continuing the migration in a new ChatGPT conversation.

The migration MUST be performed **step by step**, with one change at a time. After every step, the Raspberry Pi state must be tested and validated before moving to the next step.

The objective is to migrate the current Raspberry Pi 5 graphical startup from an Openbox autostart that directly launches the display setup, `x11vnc`, and QLC+ into a cleaner architecture based on systemd services and service-wrapper commands compatible with the service-control approach used by:

- repository: `https://github.com/infrafast/raspiLightGUI`
- service pack: `raspi_service_pack`
- wrapper model: `raspilightgui-service`

The existing desktop applications that genuinely belong to the Openbox session should remain in Openbox autostart.

# 3. Current Openbox autostart — exact known version

The following script was generated and validated during the previous work.

File previously generated by ChatGPT:

```text
autostart_pi5_resolution_selectable
```

Its exact content is embedded here so that the next conversation does **not** depend on access to an earlier generated attachment:

```bash
#!/bin/sh

# -----------------------------
# Openbox session autostart
# Raspberry Pi 5 / QLC+ 5
# -----------------------------

# ============================================================
# SCREEN RESOLUTION
# ============================================================
#
# Choose one of the following values:
#
#   SCREEN_RESOLUTION="1024x768"
#       Original/default resolution.
#
#   SCREEN_RESOLUTION="1368x768"
#       Wider desktop with the same 768 px height.
#       Recommended for VNC / QLC+.
#
SCREEN_RESOLUTION="1368x768"

case "$SCREEN_RESOLUTION" in

  "1024x768")
    /usr/bin/xrandr --output HDMI-1 --mode 1024x768
    ;;

  "1368x768")
    # CVT modeline for 1368x768 @ ~60 Hz
    # Generated with: cvt 1366 768 60
    /usr/bin/xrandr --newmode "1368x768_60.00" \
      85.25 1368 1440 1576 1784 768 771 781 798 -hsync +vsync 2>/dev/null || true

    /usr/bin/xrandr --addmode HDMI-1 "1368x768_60.00" 2>/dev/null || true
    /usr/bin/xrandr --output HDMI-1 --mode "1368x768_60.00"
    ;;

  *)
    echo "Unknown SCREEN_RESOLUTION: $SCREEN_RESOLUTION" >&2
    echo "Valid values: 1024x768 or 1368x768" >&2
    ;;
esac

# -----------------------------
# Desktop
# -----------------------------

# Desktop manager (wallpaper + desktop icons)
/usr/bin/pcmanfm --desktop &

# Taskbar
/usr/bin/tint2 &

# -----------------------------
# VNC server
# -----------------------------

/usr/bin/x11vnc \
  -display :0 \
  -auth /home/pi/.Xauthority \
  -rfbauth /home/pi/.vnc/passwd \
  -forever \
  -shared \
  -listen 0.0.0.0 \
  -xkb &

# -----------------------------
# Utilities
# -----------------------------

# Terminal
/usr/bin/xterm &

# System monitor
/usr/bin/xterm -geometry 120x40+0+0 -e /usr/bin/btop &

# -----------------------------
# QLC+ 5
# -----------------------------

/usr/bin/qlcplus-qml -3 --web --web-auth \
  --open "/home/pi/interval/QLCfiles/intervalPI5.qxw" &

```

Important current behavior:

1. Openbox starts.
2. The script applies the X11 resolution.
3. `pcmanfm --desktop` starts.
4. `tint2` starts.
5. `x11vnc` starts.
6. `xterm` / `btop` start.
7. QLC+ starts.

Current selected resolution:

```text
1368x768
```

Alternative supported resolution:

```text
1024x768
```

The custom validated CVT modeline for 1368×768 is:

```text
"1368x768_60.00" 85.25 1368 1440 1576 1784 768 771 781 798 -hsync +vsync
```

# 4. Target architecture

The desired final startup order is:

```text
BOOT
 |
 +-- LightDM
 |     |
 |     +-- autologin user pi
 |            |
 |            +-- Openbox / X11 DISPLAY=:0
 |
 +-- x11-display-setup.service
 |     |
 |     +-- wait until DISPLAY=:0 is really usable
 |     +-- apply selected resolution
 |
 +-- x11vnc.service
 |     |
 |     +-- wait for successful display setup
 |     +-- expose the existing X11 desktop through VNC
 |
 +-- qlcplus.service
 |     |
 |     +-- wait for x11vnc service
 |     +-- run qlcplus-qml as user pi
 |
 +-- raspiLightGUI / Oculizer / LiveStageAssistant / other controlled services
```

The important design principle is:

> **Openbox owns the desktop session. systemd owns infrastructure and critical applications.**

Openbox autostart must eventually contain only desktop-session applications such as:

```text
pcmanfm
tint2
xterm
btop
```

The following must eventually be removed from Openbox autostart:

```text
xrandr display setup
x11vnc
qlcplus-qml
```

---

# 5. Why x11vnc and QLC+ should NOT be started by Openbox via wrapper commands

Do **not** make the final architecture:

```text
Openbox autostart
  -> x11vnc-service start
  -> qlcplus-service start
```

That would create two competing autostart mechanisms:

```text
Openbox autostart
systemd enable/disable
```

and would make `auto` / `noauto` semantics ambiguous.

Instead:

```text
systemctl enable x11-display-setup.service
systemctl enable x11vnc.service
systemctl enable qlcplus.service
```

must be the source of truth for automatic startup.

A `noauto` command must mean that the service will **not start automatically on the next boot**.

# 6. Service wrapper convention

The new QLC+ wrapper should follow the existing `raspilightgui-service` convention from `raspiLightGUI/raspi_service_pack`.

Expected commands:

```bash
qlcplus-service start
qlcplus-service stop
qlcplus-service restart
qlcplus-service status
qlcplus-service logs
qlcplus-service auto
qlcplus-service noauto
qlcplus-service last-state
qlcplus-service health
```

Recommended semantics:

### `start`

```text
systemctl start qlcplus.service
```

### `stop`

```text
systemctl stop qlcplus.service
```

### `restart`

```text
systemctl restart qlcplus.service
```

### `status`

```text
systemctl status qlcplus.service --no-pager
```

### `logs`

```text
journalctl -u qlcplus.service -f
```

### `auto`

Enable at boot and start immediately:

```text
systemctl enable --now qlcplus.service
```

### `noauto`

Disable boot autostart **without stopping the currently running process**:

```text
systemctl disable qlcplus.service
```

### `last-state`

Report:

```text
Enabled: <enabled/disabled>
Active : <active/inactive>
```

### `health`

Return success only if the service is active.

The same wrapper philosophy can later be applied to x11vnc if desired.

# 8. QLC+ options must be easy to change

Do not hard-code operational flags inside the systemd unit.

Target configuration file:

```text
/etc/default/qlcplus
```

Recommended initial content:

```bash
QLCPLUS_OPTIONS='-3 --web --web-auth'
QLCPLUS_PROJECT='/home/pi/interval/QLCfiles/intervalPI5.qxw'
```

A launcher such as:

```text
/usr/local/bin/qlcplus-run
```

should read these environment variables and execute QLC+.

Conceptually:

```bash
#!/usr/bin/env bash
set -euo pipefail

exec /usr/bin/qlcplus-qml \
    $QLCPLUS_OPTIONS \
    --open "$QLCPLUS_PROJECT"
```

This allows easy changes such as:

```bash
sudo vi /etc/default/qlcplus
sudo systemctl restart qlcplus.service
```

without modifying the systemd unit.

Caveat for future implementation:

Using a single shell string for arbitrary arguments has quoting limitations. During implementation, verify whether the desired QLC+ options are simple enough for this approach or whether a safer argument-array/configuration strategy is preferable.

# 9. X11 readiness — no arbitrary startup delay

Do **not** use a fixed:

```bash
sleep 2
```

to wait for LightDM/Openbox.

A service must test the real X11 condition.

Target helper:

```text
/usr/local/bin/wait-for-x11
```

Concept:

```bash
#!/usr/bin/env bash
set -e

export DISPLAY=:0
export XAUTHORITY=/home/pi/.Xauthority

until /usr/bin/xdpyinfo >/dev/null 2>&1; do
    sleep 0.25
done
```

The `sleep 0.25` is only the polling interval; startup occurs immediately when X11 is genuinely ready.

For production, add a reasonable timeout so a broken graphical session does not leave a service stuck forever.

# 10. Screen-resolution management

The current `xrandr` block must be moved out of Openbox autostart into a dedicated systemd oneshot service.

Target configuration file:

```text
/etc/default/x11-display
```

Initial documented content:

```bash
# Supported values:
#   1024x768  = original/default resolution
#   1368x768  = wide desktop used for VNC / QLC+

SCREEN_RESOLUTION="1368x768"
```

Target helper:

```text
/usr/local/bin/x11-display-setup
```

Required behavior:

### If `SCREEN_RESOLUTION=1024x768`

Run:

```bash
/usr/bin/xrandr --output HDMI-1 --mode 1024x768
```

### If `SCREEN_RESOLUTION=1368x768`

Ensure custom mode exists:

```bash
/usr/bin/xrandr --newmode "1368x768_60.00" \
  85.25 1368 1440 1576 1784 768 771 781 798 -hsync +vsync
```

Attach mode to HDMI-1:

```bash
/usr/bin/xrandr --addmode HDMI-1 "1368x768_60.00"
```

Then:

```bash
/usr/bin/xrandr --output HDMI-1 --mode "1368x768_60.00"
```

The script must tolerate an already-existing mode / already-attached mode.

# 11. x11-display-setup.service

Target concept:

```ini
[Unit]
Description=Configure X11 display resolution
After=lightdm.service
Requires=lightdm.service

[Service]
Type=oneshot
User=pi
Group=pi
Environment=HOME=/home/pi
Environment=DISPLAY=:0
Environment=XAUTHORITY=/home/pi/.Xauthority
EnvironmentFile=/etc/default/x11-display

ExecStartPre=/usr/local/bin/wait-for-x11
ExecStart=/usr/local/bin/x11-display-setup

RemainAfterExit=yes

[Install]
WantedBy=graphical.target
```

Caveat:

`After=lightdm.service` alone is **not sufficient** to prove that `:0` is ready. This is why `wait-for-x11` is required.

```ini
Environment=HOME=/home/pi
```

```ini
Restart=on-failure
RestartSec=2
```

The VNC service should share the **real X11/Openbox desktop**, not create a separate virtual desktop.

This is important because a physical HDMI monitor connected to the Pi must show the same desktop as VNC.

# 13. QLC+ systemd service

Target ordering:

```ini
After=x11vnc.service
Requires=x11vnc.service
```

Target service concept:

```ini
[Unit]
Description=QLC+ 5
After=x11vnc.service
Requires=x11vnc.service

[Service]
Type=simple
User=pi
Group=pi
Environment=HOME=/home/pi
Environment=DISPLAY=:0
Environment=XAUTHORITY=/home/pi/.Xauthority
EnvironmentFile=/etc/default/qlcplus

ExecStart=/usr/local/bin/qlcplus-run

Restart=on-failure
RestartSec=3
TimeoutStopSec=10

[Install]
WantedBy=graphical.target
```

Before finalizing the service, verify QLC+ shutdown behavior under SIGTERM and whether `TimeoutStopSec=10` is suitable.

Do not use `Restart=always` initially; `Restart=on-failure` is safer while validating deliberate manual stops.

# 14. Ordering relative to raspiLightGUI and other controlled services

The desired conceptual dependency chain is:

```text
X11
 -> resolution
 -> x11vnc
 -> QLC+
 -> higher-level application services
```

Examples of higher-level services:

```text
raspiLightGUI
OculizerQLC
LiveStageAssistant
```

The current `raspilightgui.service` from the GitHub repository starts only after:

```ini
After=local-fs.target
```

During later integration it may be changed to:

```ini
After=qlcplus.service
Wants=qlcplus.service
```

Prefer:

```ini
Wants=qlcplus.service
```

instead of:

```ini
Requires=qlcplus.service
```

for the OLED/control-panel application.

Reason:

If QLC+ fails, raspiLightGUI should ideally remain alive so it can display/report:

```text
QLC DOWN
```

It should not be forcibly stopped just because QLC+ failed.

For OculizerQLC, determine its desired dependency independently during a later phase.

Create:

```text

```

```bash

sudo systemctl status x11vnc.service --no-pager
```

Validate from the Mac that VNC reconnects and displays the correct Openbox desktop.

Only after this works reliably should the x11vnc block be removed from Openbox autostart.

Create:

```text

/usr/local/bin/qlcplus-run
/etc/systemd/system/qlcplus.service
/usr/local/bin/qlcplus-service
```

The wrapper must follow the raspiLightGUI service-pack conventions.

Do not start a second QLC+ process.

Stop the existing Openbox-started instance first.

Test:


Validate:

- QLC+ GUI appears via VNC

- correct workspace is loaded
- QLC+ web interface works
- QLC+ WebSocket/API requirements still work
- stop/restart work
- logs work
- `noauto` does not stop current process
- `auto` enables boot autostart

Only after all of this should the QLC+ launch block be removed from Openbox autostart.

# 17. Important caveats

## QLC+ needs the actual graphical session

A plain system service starting too early will fail if:

```text
DISPLAY=:0
```

or:

```text
/home/pi/.Xauthority
```

is not ready.

Therefore test X11 readiness explicitly.

## Do not run duplicate processes

During migration always verify:

```bash
pgrep -af x11vnc
pgrep -af qlcplus-qml
```

before manually starting a replacement service.

## Do not remove working autostart lines prematurely

The existing Openbox autostart is the rollback path until each replacement service is validated.

## Service user

QLC+ and x11vnc should run as:

```text
pi
```

not root.

## VNC password

Keep using:

```text
/home/pi/.vnc/passwd
```

and preserve its permissions.

## Screen name

Current validated XRandR output name is:

```text
HDMI-1
```

If a future Raspberry Pi OS update renames the connector, the display setup script may need adjustment.

## Headless + HDMI

The final design must continue to support both simultaneously:

- headless boot with usable X display / VNC
- physical HDMI monitor connected and showing the same session

## QLC+ workspace typo warning

The correct known workspace extension/path from the validated autostart is:

```text
/home/pi/interval/QLCfiles/intervalPI5.qxw
```

If a future message contains `.qxe`, treat it as a likely typo unless the actual filesystem proves otherwise.

# 18. Existing raspiLightGUI service-pack model

```text

├── install.sh
├── raspilightgui-service
└── systemd/
```

```text
├── qlcplus-run
├── qlcplus.default
└── systemd/
    └── qlcplus.service
```

```text

├── x11-display-setup
├── x11-display.default

    ├── x11-display-setup.service
    └── x11vnc.service
```

Do not implement all of this in one jump in the next chat. The user explicitly wants interactive, validated migration one step at a time.
